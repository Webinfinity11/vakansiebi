## 3. სქემა, ვადა და წვდომა

წინადადება — ცალკე ცხრილი `resumes`, ცალკე `analytics_events`-ისგან (არ უნდა აირიოს ანონიმურ ცხრილთან):

```sql
CREATE TABLE resumes (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  cv jsonb NOT NULL,              -- cvSchema-ს სრული ობიექტი
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  consented_at timestamptz NOT NULL,
  consent_version text NOT NULL,  -- იხ. §4
  delete_token uuid NOT NULL DEFAULT gen_random_uuid(),
  expires_at timestamptz NOT NULL -- updated_at + 12 თვე
);
CREATE INDEX resumes_expires_at ON resumes (expires_at);
```

`jsonb` მთლიან `cv`-ს ინახავს (მარტივი, უკვე არსებული zod-სქემის ხელახლა გამოყენება); ცალკე `email`/`phone` სვეტების დამატება საჭირო იქნება მხოლოდ იმ შემთხვევაში, თუ საჭირო გახდება მომხმარებლის თხოვნით ძებნა/წაშლა ელფოსტით (მაგ. GDPR-ტიპის „მომაშორე ჩემი მონაცემები“ მოთხოვნისას ადმინს რომ არ დასჭირდეს `jsonb`-ის სკანირება).

- **ვადა**: 12 თვე ბოლო განახლებიდან (`expires_at`), შემდეგ სრული წაშლა — არა მხოლოდ დღიურ აგრეგატში ჩაკეცვა, როგორც ანალიტიკის მოვლენებთანაა (`db/migrations/014...`-ის მსგავსი 30-დღიანი rollup აქ არასწორია, რადგან CV აგრეგირებადი არაა). წაშლის job არსებული worker-ის ნიმუშით (`worker/main.ts:143`-ის მსგავსი განრიგი).
- **წაშლა/ექსპორტი მომხმარებლის მიერ**: `delete_token`-ზე დაფუძნებული ბმული ელფოსტით (მაგ. „წაშალე ჩემი რეზიუმე“ ბმული ყოველ დამახსოვრებულ CV-ზე, ისე როგორც `personal-space`-ს ძიებებს აქვს UI-დან წაშლა). ექსპორტი — იგივე `jsonb`-ის JSON/PDF სახით მოთხოვნისას.
- **წვდომა**: მხოლოდ ადმინის სესია (`ertad_admin`, `lib/server/auth.ts`); ეს დღეს **პერსონალური მონაცემია ადმინის თვალწინ** — საჭირო იქნება წვდომის ლოგირება (ვინ/როდის გახსნა კონკრეტული CV), რაც დღეს არცერთ ადმინის მოქმედებაზე არ არსებობს კოდში.
- **დაშიფვრა/ბექაფი**: Neon-ის at-rest დაშიფვრა პლატფორმის დონეზეა (აპლიკაციის კოდი ცალკე არაფერს შიფრავს — არცერთ არსებულ ცხრილში ასეთი არაა). **გადასამოწმებელია**: Neon-ის point-in-time recovery/ბექაფი მომხმარებლის მიერ „წაშლილ“ ჩანაწერს გარკვეული პერიოდით (ჩვეულებრივ რამდენიმე დღე) მაინც ინახავს ბექაფებში — ეს პატიოსნად უნდა ეწეროს თანხმობის ტექსტში ან პრივატულობის გვერდზე, „წაშლისთანავე სამუდამოდ ქრება“ არ არის ზუსტი დაპირება.

## 6. რისკი საქართველოს კანონით — არ არის იურიდიული რჩევა

„პერსონალურ მონაცემთა დაცვის შესახებ“ საქართველოს კანონი (2023 წ., ძირითადად ძალაშია 2024-03-01-დან). ქვემოთ ჩემი ცოდნა ამ ეტაპისთვის — ზუსტი მუხლების ნომრები **გადასამოწმებელია**:

- **სამართლებრივი საფუძველი**: სახელის/ტელეფონის/ელფოსტის/გამოცდილების ბაზაში შენახვას სჭირდება საფუძველი — ყველაზე უსაფრთხო აქ თანხმობაა. თანხმობა უნდა იყოს თავისუფლად მიცემული, კონკრეტული, ინფორმირებული და ცალსახა — წინასწარ მონიშნული ჩექბოქსი (`checked` ნაგულისხმევად) ამ სტანდარტს არ აკმაყოფილებს (§4-ში `unchecked` ამიტომაა).
- **მონაცემთა მინიმიზაცია**: მხოლოდ მიზნისთვის საჭირო ველი — §2-ის ცხრილი ამიტომაა საჭირო; დიზაინის ველების (`template`, `accent`...) ჩართვა ბაზაში ამ პრინციპს დაარღვევდა უმიზეზოდ.
- **შენახვის ვადა**: კანონი მოითხოვს, რომ მონაცემი არ ინახებოდეს მიზნისთვის საჭიროზე მეტხანს — 12-თვიანი წინადადება (§3) ამის დასაკმაყოფილებლადაა, მაგრამ ეს რიცხვი კონკრეტულ მიზანზეა დამოკიდებული და **გადასამოწმებელია**, გამართლებულია თუ არა სწორედ 12 თვე.
- **სუბიექტის უფლებები**: წვდომა საკუთარ მონაცემზე, გასწორება, წაშლა („დავიწყების უფლების“ მსგავსი), თანხმობის გამოთხოვა — ეს ყველა §3/§4-ის მექანიზმებს (delete_token, ექსპორტი) მოითხოვს, თანხმობის ტექსტში ცალსახად ჩამოწერილი.
- **დამუშავებაზე პასუხისმგებელი პირის ვალდებულებები**: სავარაუდოდ სავალდებულოა კონკრეტული პასუხისმგებელი პირის/საკონტაქტო არხის მითითება, სადაც სუბიექტს შეუძლია მიმართვა — თანხმობის ტექსტში „[ბმული/ელფოსტა]“ ეს არხია, უნდა იყოს რეალური.
- **განსაკუთრებული კატეგორია**: მარტო ფოტო, ჩვეულებრივ, „ბიომეტრიულ მონაცემად“ არ ითვლება, სანამ სპეციალურად იდენტიფიკაცია/ვერიფიკაციისთვის არ მუშავდება — **გადასამოწმებელია** ზუსტი განმარტება ამ კანონში. მეტი რისკია `summary`/`experience`-ის თავისუფალ ტექსტში (§2) შემთხვევით მოხვედრილი ჯანმრთელობის/რელიგიის/ეთნიკური მონაცემი — ასეთს კანონი, სავარაუდოდ, უფრო მკაცრ დამუშავებას მოითხოვს. რეკომენდაცია: გაფრთხილება ტექსტში, რომ ასეთი ინფორმაცია არ შეიტანონ.
- **საზღვარგარეთ გადაცემა**: Neon (Postgres, აშშ-ის ინფრასტრუქტურა) და Vercel — მონაცემი ტოვებს საქართველოს იურისდიქციას. **გადასამოწმებელია**, კანონი მოითხოვს თუ არა დამატებით მექანიზმს (ხელშეკრულებრივი გარანტიები, ადეკვატურობის შეფასება) ამ გადაცემისთვის.
- **ზედამხედველი ორგანო/სანქციები**: პერსონალურ მონაცემთა დაცვის სამსახური არის ზედამხედველი; 2023 წლის კანონმა გაზარდა ჯარიმების ზომები წინა კანონთან შედარებით. ზუსტი თანხები **გადასამოწმებელია**.

**ეს არ არის იურიდიული რჩევა.** დანერგვამდე საჭიროა კონსულტაცია საქართველოს კანონმდებლობის სპეციალისტთან, განსაკუთრებით საზღვარგარეთ გადაცემისა და თანხმობის ფორმულირების ნაწილში.

## 7. რეკომენდაცია

**არ დაინერგოს**, სანამ: (ა) დაზუსტდება ზუსტი მიზანი (რატომ სჭირდება CV-ის ბაზაში შენახვა — დამსაქმებელთან გაზიარება? ადმინის მოძებნა? — ეს დღეს დავალებაშივე არაა ჩამოყალიბებული და განსაზღვრავს, საჭიროა თუ არა დიზაინის ველები, `experience`-ის მთლიანი ისტორია და ა.შ.); (ბ) შეიქმნას კონფიდენციალობის გვერდი, რომელზეც §4-ის თანხმობის ტექსტი მიემართება; (გ) მიღებულ იქნას იურიდიული შეფასება §6-ის „გადასამოწმებელია“ პუნქტებზე, განსაკუთრებით საზღვარგარეთ გადაცემასა და თანხმობის ფორმულირებაზე.

**ალტერნატივა, რომელიც უკვე არსებობს**: ეტაპი 1-ის ანონიმური CV-ძაბრი (`lib/analytics-funnel.ts`, `resume` kind) უკვე იძლევა პასუხს „სად წყვეტენ CV-ის შევსებას/რომელ შაბლონს ირჩევენ“-ზე პერსონალური მონაცემის შენახვის გარეშე — თუ მიზანი პროდუქტის ანალიტიკაა და არა კონკრეტული განაცხადის შენახვა/გაზიარება, ეს ალტერნატივა შესაძლოა საკმარისი იყოს და მთელი ეს რისკი საერთოდ არ დასჭირდეს.
