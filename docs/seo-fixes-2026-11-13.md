## 7. რას არ ვასწორებთ და რატომ

- **ვაკანსიების „დუბლიკატი შინაარსი“ (Semrush 81, სათაური 173).** შემოწმებული 23 გვერდი ერთი დამსაქმებლის ერთი პოზიციაა სხვადასხვა ქალაქში ან ფილიალში (საქართველოს ფოსტის კურიერი 8 ქალაქში, კრედო ბანკი, კაუკასუს აუტო). ეს ცალკე ვაკანსიებია; canonical ყველგან საკუთარია და სწორია. ერთი და იმავე სათაურის, დამსაქმებლისა და ქალაქის ჩანაწერები უკვე ერთიანდება (`search-plan.ts`, `groupKey`) და sitemap-ში მხოლოდ მთავარი ხვდება. სათაურში ქალაქის დამატება მათ განასხვავებს. დარჩება შემთხვევები, სადაც ქალაქის ველი ცარიელია ან ფილიალის სახელია; მათი გაერთიანება ნამდვილ ვაკანსიებს დამალავდა.
- **404 (1 675).** ვადაგასული ვაკანსიები და ძველი `?from=…` მისამართებია. სერვერი ნამდვილ 404-ს აბრუნებს, რაც Google-ის JobPosting-ის წესით სწორი ქცევაა. Semrush-ში გატეხილი შიდა ბმული 0-ია. „Validate fix“-ის დაჭერა საჭირო არ არის.
- **„Crawled — currently not indexed“-ის ნამდვილი ვაკანსიები.** შემოწმებული 60-დან 57 ისევ აქტიურია; გახსნილი 14 გამართულია, JobPosting-ით, გამოქვეყნებული 23 ოქტომბრიდან 10 ნოემბრამდე და დაკრაულილი 10–11 ნოემბერს. ტექნიკური ხარვეზი არ ჩანს; ინდექსაციის გადაწყვეტილება Google-ისაა. ჩვენი მხრიდან ბერკეტია შიდა ბმულები და crawl-ის რესურსი (1–3 პუნქტი).
- **noindex (719).** განზრახაა: ძიების, დალაგებისა და ცარიელი ფილტრების გვერდები.
- **sitemap „Couldn't fetch“.** ხუთივე ფაილი 200-ს აბრუნებს სწორი XML-ითა და header-ებით; კოდში გამოსასწორებელი არ მოიძებნა. მიზეზი ისევ დაუდგენელია (იხ. `docs/google-indexing-audit-2026-11-09.md`). 1-ლი პუნქტი crawl-ის რესურსს ათავისუფლებს, მაგრამ ამ სტატუსის გამოსწორებას არ ადასტურებს.
- **კომპანიის გვერდები ერთი ვაკანსიით.** ინდექსაციის წესი ადრე დამტკიცებული გადაწყვეტილებაა (გვერდი იქმნება ერთი ვაკანსიიდან) და ფაილები სხვა ნაკადს ეკუთვნის; არ შეცვლილა.
- **Semrush-ის „Low text to HTML ratio“ (2 690) და „Blocked from crawling“ (287).** პირველი ყველა გვერდზეა და რეიტინგზე არ მოქმედებს; მეორე განზრახ დახურული მისამართებია.
- **Core Web Vitals.** Search Console-ში მონაცემი არ არის („Not enough usage data“), ლოკალურად production-ის სიჩქარე ვერ იზომება. გაშვების შემდეგ PageSpeed Insights-ით შეამოწმეთ მთავარი, ერთი landing და ერთი ვაკანსია.

## 9. production-ზე გასვლის ნაბიჯები

1. **ჯერ მიგრაცია, შემდეგ კოდი.** ახალი კოდი `search_*` სვეტებს კითხულობს და მათ გარეშე `entryLevel` და `employment` ფილტრები შეცდომას დააბრუნებს. ძველ კოდს ახალი სვეტები ხელს არ უშლის.
2. მიგრაცია 081 `jobs` ცხრილს თავიდან წერს `ACCESS EXCLUSIVE` lock-ით, როგორც 027: ამ დროს ცხრილზე კითხვაც და წერაც ჩერდება. `lock_timeout` 3 წამია (lock-ის ლოდინი), `statement_timeout` 300 წამი; ჩავარდნისას ტრანზაქცია უკან ბრუნდება. გაუშვით დაბალი დატვირთვის დროს და scraper-ის გაშვებებს შორის.
3. გაუშვით production-ის მიგრაცია ჩვეული წესით (`npm run db:migrate` production-ის `DATABASE_URL`-ით). შემდეგ შეამოწმეთ: `SELECT count(*) FILTER (WHERE search_entry_level), count(*) FILTER (WHERE search_part_time) FROM jobs WHERE status='published';` — ორივე ნულზე მეტი უნდა იყოს.
4. კოდის გაშვება: push `main`-ზე (`.github/workflows/deploy.yml`). `vercel --prod` პარალელურად არ გაუშვათ.
5. გაშვების შემდეგ შეამოწმეთ:
   - `https://jobx.ge/robots.txt`-ში Googlebot-ის ჯგუფი და ორი ახალი `Disallow`;
   - `curl -sI https://jobx.ge/vacancies/<…>/opengraph-image` → `s-maxage=86400`;
   - `curl -s -A Googlebot 'https://jobx.ge/?page=200' | grep -c 'class="pagination"'` → 1;
   - ვაკანსიის გვერდის HTML-ში სხვა `/vacancies/…` ბმულები;
   - `/?city=batumi&entryLevel=true`-ის პასუხის დრო (ადრე 4.5 წამი).
6. **ქეში.** sitemap CDN-ზე ერთი საათით ინახება, ამიტომ emoji-სათაურიანი მისამართი ერთ საათში გაქრება. landing-ების `unstable_cache` 5 წუთიანია. ხელით გასუფთავება საჭირო არ არის.
7. **Search Console.** `https://jobx.ge/sitemap.xml` ერთხელ გაგზავნეთ თავიდან, გაშვებიდან ერთი საათის შემდეგ. ხშირი ხელახალი გაგზავნა არ შველის. ორ-სამ კვირაში შეადარეთ: „Crawled — currently not indexed“-ის რაოდენობა და მასში სურათების წილი, ინდექსირებული გვერდების რაოდენობა, Crawl stats-ში მოთხოვნების განაწილება.
8. **უკან დაბრუნება.** ჯერ კოდის revert, შემდეგ `ALTER TABLE jobs DROP COLUMN search_entry_level, DROP COLUMN search_part_time, DROP COLUMN search_internship, DROP COLUMN search_daily;` (ესეც ცხრილის lock-ს ითხოვს). დანარჩენი ცვლილებები ბაზას არ ეხება.
