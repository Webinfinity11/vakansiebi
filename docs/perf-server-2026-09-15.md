4. `publicRead()` საჯარო სიის, saved availability-ის, პროფილების, ლოგოებისა და კომპანიის ცნობარის SQL-ს ასრულებს `BEGIN READ ONLY; SET LOCAL statement_timeout='10s'` ტრანზაქციაში. ეს ეხება ამავე endpoint-ის draft preview-საც. ლიმიტს PostgreSQL აღასრულებს; COMMIT/ROLLBACK pooled კავშირის წინა პარამეტრს აღადგენს, წარუმატებელი rollback-ისას კავშირი იხურება. admin/worker-ის სხვა query-ებს გლობალური პარამეტრი არ ეცვლება. `pg_sleep(11)` ინტეგრაციულ ტესტში 10 წამზე წყდება PostgreSQL `57014` შეცდომით და კავშირი შემდეგ კვლავ მუშაობს. ლიმიტი თითო SQL statement-ს ეხება, არა მთელ HTTP მოთხოვნას ან pool-ის მოლოდინს. [statement_timeout](https://www.postgresql.org/docs/16/runtime-config-client.html), [SET LOCAL](https://www.postgresql.org/docs/16/sql-set.html).
5. `scripts/perf-api.ts` ინახავს გაზომვებს, EXPLAIN JSON გეგმებსა და before/after შედარებას. დამატებული ინტეგრაციული შემოწმებები ფარავს წარმომადგენლის ტექსტს, exclude-ს, direct ID-ს, summary/countsOnly-ს, promotion-ს, draft/public გამიჯვნას და snapshot-ის ცვლილებისას generated ველების დაუყოვნებლივ განახლებას. cache ტესტი summary/countsOnly ფორმატებზეც ამოწმებს პირადი მოთხოვნების `private, no-store` საზღვარს.

არჩევანის საკონტროლო ექსპერიმენტი: მხოლოდ `jsonb_to_record` + წარმომადგენლის ტექსტი ცარიელ SQL execution-ს 577.7 → 343.5 ms-მდე ამცირებდა, მაგრამ JSON გაშლაზე ~97 ms რჩებოდა. STORED ველების დამატებით ეს ხარჯიც გაქრა; ბაზის ზომა 61 → 65 MB გახდა. გენერირებული 11 ველი 12 518-ვე snapshot-ს შევადარე — შეუსაბამობა 0.

### მიგრაცია და გაშვება

- მიგრაცია შესრულდა მხოლოდ `ertad_perf` და `ertad_test` ბაზებზე. production უცვლელია.
- **ახალი კოდის გაშვებამდე შესაბამის გარემოში აუცილებელია `020_public_search_scalars.sql`**, შემდეგ `ANALYZE jobs`. ძველი კოდი დამატებულ სვეტებთან თავსებადია, ამიტომ ჯერ სქემა უნდა განახლდეს, შემდეგ აპლიკაცია.

[Generated columns](https://www.postgresql.org/docs/16/ddl-generated-columns.html), [ALTER TABLE](https://www.postgresql.org/docs/16/sql-altertable.html).

### work_mem-ის საკონტროლო ექსპერიმენტი

მხოლოდ ლოკალური პროცესის `PGOPTIONS='-c work_mem=16MB'` პარამეტრით, იმავე snapshot-სა და საბოლოო კოდზე, თითო სცენარი 3 გათბობით და 15 გაშვებით:

|---|---:|---:|---:|---:|
| ცარიელი | 264.70/337.57 | 247.56/273.37 | 3669/2437 | 0/0 |
| q=მოლარე | 389.69/513.78 | 372.11/483.45 | 6179/3692 | 4978/2489 |

[PostgreSQL მეხსიერების პარამეტრები](https://www.postgresql.org/docs/16/runtime-config-resource.html).

მთავარი ნაკადის მოწოდებული production `pg_stat_database` — 7833 temp file / 82.5 GiB — დაგროვილი საერთო მაჩვენებელია. ჩვენი გეგმები ამ API-ში spill-ს ადასტურებს, მაგრამ მთელი 82.5 GiB-ის ამ query-ზე მიწერა შეუძლებელია statement-ების ცალკე სტატისტიკის გარეშე. ფაილები: `/tmp/perf-api-workmem16.json`, `/tmp/perf-api-workmem16-{empty,cashier}-explain.json`. მუდმივი ლოკალური ან production პარამეტრი არ შეცვლილა.
