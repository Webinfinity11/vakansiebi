## 1. რა გვაქვს ახლა

„ახალი ვაკანსია“ იხსნება `/company`-ის გვერდით პანელში (`app/company/job-editor.tsx`, `Sheet`). ეკრანის სურათები: `/tmp/jobflow/` (1440 და 390 სიგანე).

**ველები (სულ 12 + კითხვარი + განთავსება):** პოზიციის დასახელება, ქალაქი, კატეგორია, მუშაობის ფორმა, განაკვეთი, ხელფასი დან/მდე, პერიოდი, თანხის ტიპი, აღწერა, საკონტაქტო (ელფოსტა, ტელეფონი ან ბმული), ბოლო ვადა, მაქს. 5 კითხვა, განთავსება (სტანდარტული / VIP / პრემიუმი).

გვერდი არის ფოკუსირებული სამუშაო სივრცე: კაბინეტის გვერდითი მენიუ აქ არ ჩანს, ზემოთ არის მხოლოდ ვიწრო ზოლი — „ვაკანსიებზე დაბრუნება“, გვერდის სათაური და შენახვის სტატუსი. ასე მთელი სიგანე ფორმასა და გადახედვას რჩება.

შესვლის გარეშე ან `viewer` როლით გახსნისას გვერდი `/company`-ზე აბრუნებს. `noindex` რჩება.

### 3.2. ნაბიჯები

| № | ნაბიჯი | ველები | სავალდებულო |

**ნაბიჯებს შორის მოძრაობა.** „გაგრძელება“ ამოწმებს მხოლოდ მიმდინარე ნაბიჯს. ზედა ზოლში ნაბიჯზე დაჭერით ნებისმიერ გავლილ ნაბიჯზე დაბრუნება შეიძლება; წინ გადახტომაც შეიძლება, მაგრამ შეუვსებელი ნაბიჯი აღნიშნული რჩება. მონახაზი ნებისმიერ მდგომარეობაში ინახება — არასრულიც.

**იმპორტირებული ვაკანსია** (`imported`): პირველ ნაბიჯზე ჩანს მხოლოდ დასახელება და ქალაქი, დანარჩენის ნაცვლად — არსებული განმარტება, რომ კატეგორია, გრაფიკი და ანაზღაურება წყაროდან მოდის. მეოთხე ნაბიჯზე განთავსების არჩევანი გამორთულია.

### 3.3. მონახაზი და ავტომატური შენახვა

- ფორმა ინახება ცვლილებიდან დაახლოებით 1,5 წამში და ნაბიჯის შეცვლისას. ზედა ზოლში წერია: „ინახება…“, „მონახაზი შენახულია 14:32-ზე“ ან „შენახვა ვერ მოხერხდა — ხელახლა ცდა“.
- კავშირის გაწყვეტისას ასლი რჩება ბრაუზერში (`localStorage`) და კავშირის აღდგენისას იგზავნება.
- მონახაზები ჩანს ვაკანსიების სიაში ახალ ჩანართში „მონახაზები“: დასახელება (ან „უსათაურო მონახაზი“), ბოლო ცვლილების დრო და ავტორი, „გაგრძელება“ და „წაშლა“.
- მონახაზი კომპანიისაა და არა ერთი თანამშრომლის: რეკრუტერს შეუძლია მფლობელის დაწყებული ვაკანსია დაასრულოს (გადაწყვეტილება 6).
- მონახაზი მოდერაციის რიგში, საიტზე და ძებნაში არ ხვდება: ის ცალკე ცხრილშია და `jobs` ცხრილს არ ეხება.
- გაგზავნისას `requestId`-ად გამოიყენება მონახაზის `id`. ამით განმეორებითი დაჭერა ან ქსელის ხარვეზი მეორე ვაკანსიას ვერ შექმნის. წარმატებული გაგზავნის შემდეგ მონახაზი იშლება იმავე ტრანზაქციაში.

### 3.4. გადახედვა

მარჯვენა სვეტში დგას კანდიდატის ხედი და ყოველ ცვლილებაზე ახლდება: კომპანიის ლოგო და სახელი, დასახელება, ქალაქი და მუშაობის ფორმა, განაკვეთი, ანაზღაურება, ბოლო ვადა, აღწერა, ღილაკი „CV-ის გაგზავნა“ (უმოქმედო) და კითხვარი. ცარიელი ველის ადგილას ნაცრისფერი ნიმუშია, რომ გვერდი არ ხტოდეს.

მონაცემი იმავე ფუნქციით მზადდება, რომლითაც სერვერი ვაკანსიას აწყობს (`submissionVacancy`, `lib/job-submission.ts`), ამიტომ გადახედვა და გამოქვეყნებული გვერდი ერთსა და იმავე ტექსტს აჩვენებს. გადახედვა ცალკე მსუბუქი კომპონენტია და საჯარო გვერდის კოდს (`app/vacancy-page.tsx`) არ ცვლის.

გადახედვის ქვემოთ არის მოკლე სია „რა გააუმჯობესებს ვაკანსიას“ (ეტაპი B): ანაზღაურება მითითებულია, აღწერაში ჩანს მოვალეობები და მოთხოვნები, კატეგორია არჩეულია, ვადა ორ კვირაზე მეტია. სია მხოლოდ რჩევაა და გაგზავნას არ აბრკოლებს. დაუდასტურებელ სტატისტიკას არ ვწერთ.

### 3.5. გაგზავნის შემდეგ

იმავე გვერდზე ფორმის ნაცვლად ჩნდება დასკვნითი ეკრანი:

- სათაური: „ვაკანსია გაგზავნილია შესამოწმებლად“.
- რა მოხდება: „JOBX-ის გუნდი განცხადებას შეამოწმებს და გამოაქვეყნებს. შედეგს ელფოსტით შეგატყობინებთ, სტატუსს კი ვაკანსიების სიაში ნახავთ.“ შემოწმების ვადას არ ვახსენებთ (გადაწყვეტილება 3).
- ფასიანი განთავსებისას: ინვოისის ბმული და განმარტება, რომ ვადა ჩარიცხვის დადასტურებიდან აითვლება.
- ღილაკები: „ვაკანსიების სია“, „კიდევ ერთი ვაკანსიის დამატება“, „მსგავსი ვაკანსიის შექმნა“ (ასლი).

გამოქვეყნებული ვაკანსიის რედაქტირებისას ტექსტი სხვაა: „ცვლილებები გაგზავნილია შესამოწმებლად. დადასტურებამდე საიტზე მიმდინარე ვერსია დარჩება.“

## 7. რა იცვლება API-სა და ბაზაში

### ბაზა — მიგრაცია `083_company_job_drafts.sql`

ბოლო მიგრაცია ახლა `082_company_google_sign_in.sql`-ია. თუ ეტაპ 2-ის დაწყებამდე სხვა თრედი 083-ს დაიკავებს, ნომერი შესაბამისად გაიზრდება.

```sql
CREATE TABLE company_job_drafts (
  id uuid PRIMARY KEY,
  company_key text NOT NULL,
  job_id uuid REFERENCES jobs(id) ON DELETE CASCADE,  -- NULL = ახალი ვაკანსია
  form jsonb NOT NULL,
  step smallint NOT NULL DEFAULT 1,
  updated_by uuid NOT NULL,                            -- company_accounts.id
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX company_job_drafts_company_idx ON company_job_drafts(company_key, updated_at DESC);
CREATE UNIQUE INDEX company_job_drafts_job_idx ON company_job_drafts(job_id) WHERE job_id IS NOT NULL;
```

რატომ ცალკე ცხრილი და არა `jobs.status='draft'`: `jobs`-ს კითხულობს ძებნა, sitemap, ადმინის რიგი, დუბლიკატების ძებნა და ინდექსაციის რიგი. ახალი სტატუსი ყველა ამ ადგილას ფილტრის შემოწმებას მოითხოვდა და შეცდომის ფასი არაგამოქვეყნებული ვაკანსიის საიტზე გამოჩენა იქნებოდა. ცალკე ცხრილი არცერთ მათგანს არ ეხება და მარტივად უკან ბრუნდება.

JobPosting-ში გამოცდილება აისახება `experienceRequirements`-ით მხოლოდ მაშინ, თუ ამას Google-ის დოკუმენტაცია ადასტურებს; ენებისთვის JobPosting-ს ცალკე ველი არ აქვს და ისინი მხოლოდ გვერდზე ჩანს. იმპორტირებულ ვაკანსიაზე ეს ველები არ იცვლება.

## გამარტივება, 2026-11-16

R12 ცვლის ზემოთ აღწერილ ოთხნაბიჯიან პროცესს ორი ნაბიჯით: **ვაკანსია** და **გადახედვა და გამოქვეყნება**. პირველზე სავალდებულოა დასახელება, ქალაქი (დისტანციურისთვის არა) და აღწერა. განაკვეთი სრულია; ახალი ვაკანსიის საკონტაქტო, ქალაქი, ფორმა და კატეგორია ბოლო ვაკანსიიდან ივსება, საკონტაქტოს სათადარიგო მნიშვნელობა ანგარიშის ელფოსტაა. ვადა დღეიდან 30 დღეა. დამატებითი ველები დაკეცილია. აღწერა ერთი ტექსტური ველია; ჩასმული სიების ნიშნები და ხაზები ინახება. ფაილის იმპორტი არ ემატება.

მეორეზე კანდიდატის ხედი და განთავსების არჩევანია; ახალი ვაკანსიისთვის სტანდარტული უფასო განთავსება მონიშნულია. მთავარი მოქმედებაა „შესამოწმებლად გაგზავნა“. ვალიდაცია მხოლოდ blur-ის ან გაგრძელება/გაგზავნის შემდეგ ჩანს. ასლი, რედაქტირება და მონახაზი თავიანთ მონაცემებს ინარჩუნებს. ძველი 1/2 ნაბიჯი ახალ პირველზე, 3/4 — მეორეზე გადადის; ახალი მონახაზის JSON-ში wizardVersion=2 ინახება. ბაზის მიგრაცია არ არის საჭირო. საჯარო გაგზავნის სქემა უცვლელია; საკონტაქტო და ვადა სერვერზე კვლავ მოწმდება.
